# iPhone 808 Simulator 产品与技术调研

调研日期：2026 年 10 月 20 日。目标平台为 iPhone / iOS，暂以可独立运行、可上架的音乐创作工具为假设。

本报告依据 Roland 原机资料、Apple 开发文档、开发者官网、App Store 产品页和音频建模论文。竞品功能为厂商标称，未进行购买实测、音质盲听或真机延迟测量。产品定位、实现选择、验收指标和工期均为本项目建议，不能视为已经验证的性能或市场结论。

## 1. 立项判断

可以实现。iOS 已有音频生成、混音、离线渲染和音频插件所需的原生能力；现有竞品也证明了此类产品在 iPhone 上的可行性。Apple 的 [Audio Engine 文档](https://developer.apple.com/documentation/AVFAudio/audio-engine)覆盖这些能力。

建议定位为：**适合 iPhone 操作的经典 808 鼓机，保留核心声音、步进编程、重音与填充，在此基础上提供可靠保存和导出。**

首版重点是声音、节奏和触控体验。完整电路仿真、专业插件生态和大量扩展音色应单独规划。单纯复刻面板已有直接竞品；中文界面也不足以单独构成优势。

本项目的“808”指经典鼓机及其工作流。现代 Trap 中可按音高演奏、滑音的“808 Bass”可以以后扩展，不能用一个低音合成器代替整台鼓机。

## 2. 原版功能基线

**首先区分音色、乐器通道和步进。** 原机有 16 种打击乐音色，但通过 11 个乐器通道组织，其中 5 组共享通道并通过开关选音；另有 Accent 重音编程。16 个步进按键不是 16 个独立鼓轨。下表按原机控制组织，参数与配对依据 [Roland 技术规格](https://support.roland.com/hc/en-us/articles/201963539-TR-808-Technical-Specifications)。

| 通道 | 可用音色 | 原机核心控制 |
| --- | --- | --- |
| BD | 底鼓 | Level、Tone、Decay |
| SD | 军鼓 | Level、Tone、Snappy |
| LT / LC | 低通鼓 / 低康加鼓 | Level、Tuning |
| MT / MC | 中通鼓 / 中康加鼓 | Level、Tuning |
| HT / HC | 高通鼓 / 高康加鼓 | Level、Tuning |
| RS / CL | 边击 / 响棒 | Level |
| CP / MA | 拍手 / 沙锤 | Level |
| CB | 牛铃 | Level |
| CY | 镲 | Level、Tone、Decay |
| OH | 开镲 | Level、Decay |
| CH | 闭镲 | Level |

经典模式应保持共享通道的选音关系。将全部音色变成可同时独立编程的 16 条轨道，应明确标记为扩展模式。

原机工作流还包括：16 键步进输入、通过两个部分构成最多 32 步的节奏、预分拍设置、A/B 变化与 AB 交替、基本节奏与 Intro/Fill、自动填充和节奏串联成曲。存储组织为 12 个基本节奏位置及 4 个 Intro/Fill 位置，各有 A/B；歌曲有 12 条轨道、每条 64 小节。原机操作及存储语义以 [TR-808 原版说明书](https://cdn.roland.com/assets/media/pdf/TR-808_OM.pdf)为基准，不能拿 Roland Cloud 软件版的新增功能当作原机能力。

原机速度范围为 40–300 BPM；自动填充可设每 2、4、8、12、16 个小节触发。这些可以保留为经典模式默认值，依据同一份 [Roland 规格](https://support.roland.com/hc/en-us/articles/201963539-TR-808-Technical-Specifications)。

**两处容易混淆的语义：**

- Accent 是独立的重音编程及总强度控制，不能仅用“每个音符都有 MIDI 力度”代替。底鼓的电路研究显示，重音参与触发信号；若追求声音还原，需要校准它对声音的影响，而非只做输出增益。[DAFx 底鼓建模论文](https://dafx.de/paper-archive/2014/dafx14_kurt_james_werner_a_physically_informed%2C_ci.pdf)
- 原机 TAP 按钮承担填充等操作；App 中常见的 Tap Tempo 应作为独立交互设计。原机功能与按钮语义见 [原版说明书](https://cdn.roland.com/assets/media/pdf/TR-808_OM.pdf)。

Swing、逐步力度、参数锁定、触发概率、失真效果、MIDI、AUv3、Ableton Link 和 WAV 导出应作为现代扩展规划。原机物理分轨输出可在软件中用音频分轨表达；DIN 同步和电压触发需要外部硬件，不能承诺由手机接口直接等效输出。

**更值得验证的产品假设：**

1. 新用户能在一分钟内从空白创建并播放一个节奏。
2. 在小屏 iPhone 上，选鼓、写步进、调音色都能准确完成。
3. 新手可通过中文讲解理解 Accent、Decay、Fill 等概念，而不只是看到翻译后的标签。
4. 用户能快速把作品带入其他音乐应用，或导出供视频、编曲使用。

这些是待验证假设。建议找 5–8 名目标用户，覆盖新手、808 爱好者和 iOS 音乐用户，观察相同任务的完成时间和误操作。当前调研不足以判断市场规模或付费转化率。

## 4. 推荐的版本范围

### 可用首版：形成完整创作闭环

| 模块 | 建议首版范围 | 验收结果 |
| --- | --- | --- |
| 声音 | 16 音色、经典 11 通道组织、对应参数、Accent | 参数能听到有效变化；配对选音和保存恢复一致 |
| 编程 | 16 键编辑、1–32 步、预分拍、播放位置提示 | 能编辑两个部分；不丢步、不重复触发 |
| 变化 | A/B 与 AB 交替、手动及自动 Fill | 在约定的小节边界切换，填充后正确返回 |
| 编曲 | Pattern 串联、重复次数、播放/停止 | 可形成并重放一段完整节奏编排 |
| 工程 | 新建、命名、保存、自动恢复、复制、清空、撤销 | 重启后工程及鼓组参数完整恢复 |
| 输出 | 整段或整曲 WAV 导出、系统文件与分享入口 | 导出节拍和长度正确，可在其他应用打开 |
| 体验 | 横竖屏适配、中英术语、少量可编辑示例、简短入门 | 用户能完成创建—编程—保存—导出的流程 |
| 音频生命周期 | 来电/中断、锁屏策略、路由改变、引擎恢复 | 不出现持续失声、意外重复播放或工程损坏 |

可加入成本较低的现代操作：Mute/Solo、Tap Tempo、复制粘贴。Swing 可以作为独立开关加入；有它时必须明确关闭状态对应直拍。

首版不必机械限制为原机存储容量，可以使用多个工程及现代文件管理。是否提供完整的“原机面板操作模式”应在可用性测试后决定。

### 专业扩展：根据目标用户排序

- **AUv3 乐器插件**：让宿主加载鼓机；实现 MIDI 输入、宿主速度/播放同步、参数自动化、工程状态恢复、多实例隔离。音频分输出逐个宿主验证。Apple 以音频单元扩展提供这类能力。[AUv3 官方文档](https://developer.apple.com/documentation/audiotoolbox/audio-unit-v3-plug-ins)
- **Core MIDI**：外部触发、MIDI Learn，按需求增加 Clock 同步及 MIDI 文件导出。MIDI 接入与音频导出是不同功能。[Core MIDI 文档](https://developer.apple.com/documentation/coremidi)
- **Ableton Link**：连接其他应用/设备的节拍与速度；需独立验证加入、退出、变速和中断恢复。[Link 文档](https://ableton.github.io/link/)
- **创作扩展**：64 步、逐步力度、参数锁定、概率、微时序、分轨导出、适量效果。应保持经典模式的默认行为可辨认。

若首批用户就是 AUM、GarageBand 等宿主的使用者，应把 AUv3 提前到首发范围，并增加集成时间；面向普通新手则可以先发布独立版。

## 5. 声音实现路线

以下为工程取舍分析，不是对具体库或实现的实测结论。

| 路线 | 优势 | 主要代价 | 适合阶段 |
| --- | --- | --- | --- |
| 采样 | 能较快获得可信的单次击打；便于控制首版范围 | 单个采样难覆盖 Tone、Snappy、Decay 的连续变化；需要多采样或分层素材 | 概念验证、首版 |
| 算法合成 | 参数连续、占用素材少、便于扩展 | 要逐个校准起音、频谱、包络与重复触发行为；“能发声”远不等于“像 808” | 有 DSP 能力时持续建设 |
| 电路建模 | 有机会重现非线性、重音与器件交互 | 建模、数值稳定、计算优化和对照测试工作量大 | 高保真目标的专门阶段 |
| 混合 | 核心声部合成，其余采样或分层，各取所长 | 要统一音量、参数手感、资源管理和保存格式 | 推荐首版路线 |

**建议：先做混合引擎。** 优先验证底鼓的合成或高质量多采样；金属打击声、拍手等按团队经验选择合成、分层采样或多采样。以统一的声部接口封装，之后可以逐个替换。

不要只给一份 WAV 改播放速度，就宣称实现了全部原机旋钮。Decay 需要包络处理，Snappy 需要可控制的响弦成分或对应素材，Tone 的响应需要听感校准。采样方案的参数范围要如实限定。

音质验证至少覆盖：底鼓短/长衰减，军鼓响弦变化，快速连续触发，Accent 开关，多声部叠加，以及开闭镲的截音和同刻触发优先级。后两项应与参考设备或可信录音逐项校准。

严格还原不能简化为“正弦波加包络”。2014 年的 [TR-808 底鼓电路建模研究](https://www.dafx.de/paper-archive/search?author%5B%5D=Smith%2C+J.+O.&years%5B%5D=2014)已经对多个子电路和可弯折行为进行分析，可作为后续深入方向；论文可用不等于其中代码或第三方素材已获得本项目分发授权。

## 6. iOS 技术方案

**推荐：Swift / SwiftUI 原生界面，按需使用 UIKit 自定义触控控件；AVAudioEngine 管理音频图；独立的音序器与声部内核负责播放。** 如果需要长期复用 DSP 或严格控制实时路径，可用 C++ 内核，通过薄桥接层接入 iOS。

Apple 提供音频源节点和自定义音频单元能力，能接入自定义音频生成逻辑，参见 [Audio Engine](https://developer.apple.com/documentation/AVFAudio/audio-engine)及 [AVAudioSourceNode](https://developer.apple.com/documentation/avfaudio/avaudiosourcenode)。

建议边界如下：

```text
SwiftUI / UIKit 操作界面
        ↓ 编辑工程、提交带时间信息的控制事件
工程状态 / 非实时事件整理
        ↓ 有界队列、快照
音频渲染时钟 → 步进事件 → 声部引擎 → 混音/主输出处理 → 音频设备
                            ↑
                     预加载的采样与参数

工程快照 → 离线音频渲染 → WAV 文件
渲染位置 → 界面播放位置显示

后续 AUv3 适配层复用同一音序器与声部内核
```

**时钟由音频驱动。** 不用界面 Timer 或屏幕刷新回调来触发鼓声。事件在音频缓冲区内按采样位置处理；界面读取播放位置。固定速度下，十六分音符间隔为 `60 / BPM / 4` 秒；120 BPM 时为 125 ms。在非整数采样间隔时保留小数位置，避免每步舍入误差长期累积。这是建议实现，不是某个 API 自动保证的性能。

**实时路径必须受控。** 采样预加载；渲染回调内避免文件读写、网络、锁、日志和动态分配；参数更新使用安全队列或快照并做必要平滑。Apple 明确要求实时音频回调避免阻塞操作。[Apple QA1715](https://developer.apple.com/library/archive/qa/qa1715/_index.html)

**延迟需要真机测量。** 可以从 48 kHz、128/256 帧的配置实验；两种缓冲时长约为 2.67/5.33 ms，但都不等于触摸到听到声音的总延迟。实际采样率和缓冲时长必须在音频会话激活后读取，并随路由变化重新处理；Apple 明确说明 preferred 值只是请求。[Apple QA1631](https://developer.apple.com/library/archive/qa/qa1631/_index.html)

蓝牙耳机应单独测试并呈现实际适用性；低延迟演奏验收优先使用内置扬声器及有线/USB 音频设备。不能把内部时序准确等同于端到端延迟低。

**AUv3 从一开始预留边界。** 参数用稳定标识，工程格式有版本，声部引擎不依赖界面。独立模式管理自身音频会话；插件模式服从宿主的渲染、采样率和传输控制，避免两套时钟同时驱动。独立版可先用 SourceNode 适配层，后续再实现复用内核的 AUAudioUnit 适配层，仍需预留集成测试时间。

**AudioKit 可选。** 可用于加速音频图和部分组件原型；其主仓库是 MIT 许可。但它不是开箱即用的高保真 TR-808，选用的其他包、DSP 组件和素材仍要分别核对。[AudioKit 官方仓库](https://github.com/AudioKit/AudioKit)

**不优先从网页套壳或跨平台界面开始。** 这是针对 iPhone 优先、实时音频为核心、未来可能支持 AUv3 的项目取舍；跨平台框架并非不能实现，但关键音频能力仍需要原生集成，未必减少首版总工作量。

**不新增 Inter-App Audio 依赖。** 它在 iOS 13 已被弃用，新产品优先考虑 AUv3。竞品还列出 IAA，不代表新项目应照单接入。[Apple 弃用说明](https://developer.apple.com/documentation/bundleresources/entitlements/inter-app-audio)

## 7. iPhone 交互建议

采用“保留 808 的辨识度，按手机重新组织操作”的方向。深色面板、分组颜色、旋钮反馈和步进灯可以保留；不把整台硬件等比例缩小到屏幕中。

- **竖屏**：当前鼓声与少量参数在上方；步进采用两行各 8 步；32 步通过明确的部分切换编辑。优先保证单手操作及足够触控面积。
- **横屏**：一排 16 步及更多参数，适合编程与表演；仍需测量安全区内实际可用宽度。
- **旋钮**：以垂直拖动为主，显示当前值；提供精调、重置和无障碍调节。验证“手指遮挡数值”和误触问题。
- **状态反馈**：当前编辑的乐器、当前播放步、已启用步进、待切换 Pattern、待播放 Fill 使用可辨认的状态，不能只依赖颜色。
- **基础页面**：鼓机、Pattern/编排、工程/导出即可。避免首版因大量页面跳转打断创作。

例如 390 pt 宽的竖屏，扣除左右各 16 pt 后，把 16 个按键排成一行，单键平均只有约 22.4 pt，尚未扣间隙。Apple 对按钮建议一般至少提供 44×44 pt 的点击区域。因此竖屏优先两行 8 步是有空间依据的设计判断。[Apple 按钮指南](https://developer.apple.com/design/human-interface-guidelines/buttons)

“中文友好”的验证任务可以是：用户不看长说明，能理解衰减、响弦、重音与填充，完成一个示例的修改并导出。EGDR808 已列出中文支持，因此本项目需要验证教学质量和操作效率，而不是把翻译本身当作独占卖点。

## 8. 验收与测试建议

这些是拟定的验收目标，尚未运行测试。

| 方面 | 可执行的验证 |
| --- | --- |
| 时序 | 在固定 BPM、多种预分拍和实际支持的采样率下，离线检查事件时间；对照理想时间的舍入位置，目标误差不超过 1 个采样；额外覆盖非整数 BPM、循环边界及长时间播放 |
| 切换 | 检查 AB、手动 Fill、自动 Fill、Pattern 切换和 Song 循环；触发次数与边界一致，无意外双击或漏击 |
| 音质 | 对同组参数做响度匹配后的参考试听；覆盖参数最小/中间/最大值、重音和连续触发；不宣称未经盲测的“完全一致” |
| 实时性能 | 在最低支持真机上，满编鼓声、快速调参、界面滚动情况下连续播放至少 60 分钟；记录音频异常、CPU、温度和内存趋势 |
| 延迟 | 区分事件调度、音频输出与触摸到发声；按设备/路由记录实测值，独立列出蓝牙结果，不以缓冲时长代替总延迟 |
| 存储 | 保存/重启/恢复后声音参数、步进、选音、填充和编排一致；覆盖旧版本工程迁移和异常退出 |
| 导出 | 循环导出严格整小节；整曲可选择保留尾音。120 BPM、4/4 的 4 小节基础时长应为 8 秒，尾音另算；确认头尾无意外截断 |
| 系统行为 | 静音开关、锁屏、耳机拔插、USB 路由、来电中断和音频服务重置后的行为符合产品约定 |
| 插件阶段 | 至少在拟支持的 GarageBand / AUM 等宿主真机验证加载、自动化、多实例、速度变化、保存恢复及分输出；不默认宿主能力完全相同 |

## 9. 工期、设备与发布

**粗估前提：** 1 名有 iOS 实时音频经验的全职开发者，有可用 Mac 与 iPhone，采样来源已经解决，UI 范围受控；必要时有音色设计协助。以下是工程估算，不是外包报价或交付承诺。

| 阶段 | 预计时间 | 交付及决策依据 |
| --- | --- | --- |
| 声音/时序验证 | 1–2 周 | 4 个代表声部、16 步播放、参数调节、真机运行；确认声音路线和事件调度 |
| 核心功能 | 4–6 周 | 全音色、核心参数、32 步、变化/填充、歌曲编排、工程保存 |
| 完善与测试 | 3–4 周 | 手机适配、导出、恢复、中断和路由测试、示例、内测修复 |
| 专业扩展 | 另计约 4–8 周 | AUv3、MIDI、宿主联调；Link 根据需求单独排期 |

因此，可用独立首版可按 **8–12 周** 建立初步计划；若需同时学习 iOS 或 DSP，应重估。全音色电路建模需要独立研究阶段，不宜套用这个时间表。

当前工作目录在 Windows。Windows 可用于调研、设计及部分通用内核开发；标准 iOS 构建、签名和设备调试需要可用的 Mac/Xcode 环境。具体 macOS 与 Xcode 配套要求见 [Apple 系统要求](https://developer.apple.com/xcode/system-requirements/)。模拟器不能替代真机音频验收。

Apple 已公布自 2026 年 4 月 28 日起，App Store Connect 上传的 iOS 应用需使用 iOS 26 SDK 或更高版本构建；提交时应再次核对要求。**构建 SDK 与最低运行 iOS 版本是两项不同配置**，可以另外评估把最低运行版本设为 iOS 17 或 18，不必因为构建 SDK 升级而仅支持最新系统。[SDK 最低要求公告](https://developer.apple.com/news/?id=ueeok6yw)

发布预算除开发时间外，主要包括 Mac/真机条件、音源制作或授权、设计及音质验证。Apple Developer Program 标示年费为 99 美元或可用地区本币价格；这是分发会员费用，不是购买音色的费用。[Apple Developer Program](https://developer.apple.com/programs/)

## 10. 素材、品牌和商业方式

使用自有产品名、图标和界面表达。将 Roland / TR-808 用作参考说明前应核对相关权利与商店呈现，不暗示官方关系。采样要来自自己制作或明确覆盖“嵌入应用并随应用分发”的授权；“可用于音乐作品”的素材许可不能自行理解为允许打包音源售卖。Apple 的 [审核指南 4.1 与 5.2](https://developer.apple.com/app-store/review/guidelines/)分别涉及模仿应用与知识产权要求。

## 11. 开发前最有价值的验证

优先做一个 1–2 周的声音与时序原型：底鼓、军鼓、拍手、开闭镲，配 16 步播放、Accent、核心旋钮和短 WAV 导出。它是技术验证，不是首版功能缩减承诺。

通过三项结果再锁定正式方案：目标用户认可声音与参数变化；最低目标真机播放和调参稳定；新用户能快速完成一段节奏并导出。同时确定 Mac/真机条件、素材来源以及首发是否必须支持 AUv3。

现阶段可以确定技术上可行，建议采用原生 iOS 与混合音源路线。仍需验证的是声音质量、操作效率、性能边界和用户付费意愿；这些应由可试听原型及目标用户测试回答。

## 12. 音频质量保障方案

本节进一步细化质量验收。以下是待实施的方案；当前尚未获取本项目的参考音源、实现声音引擎或完成真机测试。

**先固定声音参照。** 优先获取可用于本项目的原机直录及参数记录；也可使用来源清楚的高质量参考素材。记录设备、输出接口、录音链路、旋钮位置、Accent 与触发间隔，避免把不同录音条件混为同一基准。参考保留无损文件，不用经过社交平台压缩、混响或母带处理的音乐片段来校准鼓声。原机个体本身会有差异，底鼓研究也讨论了这种差异，因此应明确本项目对齐的参考设备或声音集合。[DAFx 原始研究](https://dafx.de/paper-archive/2014/dafx14_kurt_james_werner_a_physically_informed%2C_ci.pdf)

**每个声部都检查参数变化。** 对适用参数的最小、中间、最大值及关键组合录制参考；同时覆盖普通击打、Accent 和前一次声音未结束就再次触发。底鼓关注起音、音高走向和衰减；军鼓关注鼓身与响弦比例；拍手关注瞬态结构；镲类关注频谱、尾音与截音。不会仅通过默认预设的单次击打就判定整个声部合格。

**在信号处理中保留声音特征。** 内部采用浮点处理并安排混音余量；采样编辑保留起音和足够尾音；连续参数变化做适当平滑，截音采用经校准的过渡处理，避免引入额外点击。模拟声源或失真若出现混叠，针对相应环节选择带限方法或局部过采样，并实测 CPU 与声音变化。过采样用于控制非线性处理的混叠，是有成本的处理选择。[JUCE DSP 过采样说明](https://docs.juce.com/master/classjuce_1_1dsp_1_1Oversampling.html)

保护限幅与音色失真应明确区分。默认预设保持足够余量；如果加入保护限幅，验证它没有明显压扁鼓声起音。经典音色本身的谐波与非线性应按参考保留，不能以“所有失真都消除”为目标。

**测量与试听分开验收。** 波形、频谱、频带能量、起音和衰减曲线用来发现偏差；最终听感通过响度匹配、随机编号的 A/B 文件评估。单声部之外，还要试听相同的整段节奏。测量相近不能单独证明听感相同，能够分辨两份音频也不自动表示其中一份质量更差。

| 质量项目 | 拟定的发布门槛 | 留存证据 |
| --- | --- | --- |
| 音色与旋钮 | 所有声部通过参数与重复触发检查；与参考有明显偏差的项目修正或明确限定范围 | 参数清单、参考/生成 WAV、分析图及试听记录 |
| 信号完整性 | 指定测试集无 NaN/Infinity、非预期削波、额外点击或意外截断尾音 | 自动分析结果、异常音频片段 |
| 事件时序 | 固定速度离线事件时间对理想采样位置误差不超过 1 个采样；覆盖分数 BPM、循环和 Fill | 事件日志及触发次数对照；该指标不代表总延迟 |
| 真机稳定性 | 最低支持真机在预设压力场景连续运行至少 60 分钟，无检出的漏击、断音和额外爆音；长时间运行无异常内存增长趋势 | 设备、系统、路由、缓冲配置及性能记录 |
| 导出一致性 | 同一工程复用同一声音内核；验证时固定随机种子与事件，检查实时路径和离线路径结果；导出 24-bit PCM WAV | 原工程、测试配置、输出文件和差异结果 |
| 版本回归 | 引擎改动后重新渲染固定测试工程，检查声音与节奏变化；有意调整音色时记录基准变更原因 | 基准文件、差异报告及变更记录 |

固定随机种子只用于可重复测试；带噪声或模拟变化的音色不要求每次演奏波形完全相同。与原机噪声的比较以统计特征和听感为主，不要求逐采样相减为零。

导出可以使用 Apple 的离线渲染能力，避免把播放设备或麦克风录音链路带入文件。采样率及声道格式显式指定，重采样与位深转换纳入测试；WAV 格式或较高位深本身不能补救不合格的音源。[Apple 离线渲染示例](https://developer.apple.com/documentation/avfaudio/performing-offline-audio-processing)

**播放设备分别验收。** 音色及低频判断以可靠的耳机或监听设备为主，手机扬声器检查实际使用体验。蓝牙路线单独测量，触摸到发声的延迟与内部事件精度分别报告。音频会话激活后读取实际采样率和缓冲时长，切换设备后重新适配。[Apple 音频会话说明](https://developer.apple.com/library/archive/qa/qa1631/_index.html)

开发交付应包含可试听音频、参数记录与检测报告。代码与自动分析可以验证大量工程问题；原机对照、主观音色认可和真实 iPhone 的运行表现，必须依赖实际素材、试听者与设备，不能在这些证据缺失时承诺“100% 还原”。

## 13. 音源从哪里来、怎样低成本取得

### 免费公开库怎样安全筛选

Freesound 的主要授权含 CC0、CC BY、CC BY-NC。该平台说明 CC BY 可在署名并履行其余条件后使用，CC0 更宽松；CC BY-NC 仅允许非商业用途，不适合作为计划商业上架的默认选择。[Freesound 授权说明](https://freesound.org/help/faq/)，[Creative Commons 授权解释](https://creativecommons.org/share-your-work/cclicenses/)

推荐搜索步骤：

1. 筛选 **CC0** 或 **CC BY**；把每种鼓声分开检索（如 TR-808-style kick、snare、clap、open hi-hat），不要默认搜索标签的作者确实拥有被采录设备或声音的全部权利。
2. 阅读单条声音页面和附件说明，排除上传了他人采样包、商用鼓机 ROM、歌曲切片，或授权不明确的文件。保留来源页面与作者授权信息。用户上传即使选了 CC0，也不等于其有权对第三方录音作此授权。[Creative Commons 的授权前提](https://creativecommons.org/share-your-work/cclicenses/)
3. CC BY 音频须在 App 的易找到位置列出作者、作品名、原始链接、CC BY 版本及改动说明；按该音源许可保留署名。无署名路径优先使用核对过的 CC0。CC0 添加来源致谢仍有利于溯源。
4. 商用计划排除 BY-NC。首版也建议不混用 BY-SA 或 BY-ND，除非已逐项确认改编及再分发条件与应用发行形式匹配：SA 对改编作品有相同条件，ND 仅允许以未改编形式分发。[Creative Commons 许可条件](https://creativecommons.org/share-your-work/cclicenses/)
5. 逐个试听后进行一致的剪辑、响度和尾音处理。把署名信息存在音源清单中，附在 App 的第三方许可页与项目归档里；日后有人要求撤下或更换时可找到依赖它的工程与预设。

Freesound 页面搜索结果不等于合适的 808 音色库。库中的声音可能来自合成器、爱好者克隆、其他采样库，录音响度、音色及衰减时间也可能差异很大。免费文件适合先做互动原型与教程预设；正式经典音色仍要通过前述参考录音和逐声部验收。

### 适合本项目的低成本组合

1. **零许可费原型：** 自行写简单音源合成底鼓、军鼓和通鼓；从文件明确可复用的 CC0 声音补充 clap、maracas 及部分镲声；逐个收录许可来源。把声音标为“808 风格原型”，先让开发和用户测试编曲流程。
2. **可商用首版：** 保留自行开发且经过质量校准的核心声部；缺少的声音选用 CC0 / 允许商业再分发的 CC BY 文件，或委托补录。将免费素材逐个替换成统一录制/参数体系的授权音源，是提升整套声音一致性的主要途径。
3. **更接近原机：** 借用或租用有使用权限的 TR-808 与干净录音链路，自己逐个采 Accent、Tone、Decay、Snappy 档位；或联系专业采样商购买针对 iOS App 捆绑的书面授权。不要把从 Roland Cloud、Serato 包或商业鼓机中提取的声音直接移植。

App 上架通常会把音源一并送到用户设备；因此“允许个人使用或制作新音乐”的文字不足以确认这项用途。以上为制作流程建议，不替代发行地区的法律意见；对高保真商业版本，最快的风险控制通常是自制音源，或向权利人拿到明确的嵌入式软件授权书。
